# Cumulative authoring and maintenance comparison

Historical study plan. Raw captures and obsolete replay setups were later removed under the
[retention policy](../../../docs/research/agent-evidence-retention.md). Capture instructions below describe execution, not a retention requirement.

## Question and stopping rule

Does the installed library repay its discovery cost through less styling, repair and maintenance
work than React/CSS alone? This is one bounded application sequence, not an estimate of lifetime
cost or a recurring evaluation suite. Whitney authorized continuing the evaluation after the
board-inspector experiment failed to show fewer total tokens.

Use two conditions, native React/CSS and the current installed library with the approved README.
Do not add the experimental Dialog API or guidance prototypes. Both apps begin with identical
React/TypeScript/Vite source scaffolds. Only the library dependency differs. Native elements are
allowed in both conditions; no other component libraries are available. No prompt names a guide.
The frozen initial and maintenance briefs are in `../prototypes/lifecycle/`.

Run one initial build per condition, independently inspect both, then allow at most one correction
turn per condition if measured defects remain. Apply the same maintenance brief in fresh contexts
to the resulting apps. Independently inspect again and allow at most one final correction turn
per condition. Initial and maintenance runs have eight-minute limits; correction runs have
four-minute limits. Maximum eight authoring runs. No reruns to improve results. Preserve any
interruption and missing usage; no coordinator repairs to consumer code. An incomplete app cannot
claim savings against a complete one. If initial core behavior remains unusable after correction,
stop that condition and report incomplete rather than inventing maintenance results.

Every stage uses the same fixed model, configuration and tools. Fresh contexts represent a later
coding session and avoid carrying one condition's longer conversation into maintenance. Starting
snapshots include any previous authored checks. Token totals include all authoring stages and
repairs, but exclude coordinator/evaluator work, reported separately as outside the measure.
Preinstalled scaffolding and dependencies are setup, not task work. Each app gets a dedicated port.
The runner isolates subprocess sessions and preserves timeout/interruption records.

## Acceptance and correction policy

Check both widths, data and counts, search/empty recovery, edit save/trim/invalid input/cancel/
Escape, modal focus and containment, deletion/cancel and focus destinations. Maintenance adds
initial dark appearance, a working light toggle, theme propagation into both dialogs, duplication
identity/order/edit/delete isolation, long names, and preservation of initial behavior.

Independently inspect screenshots and computed geometry, text contrast, and sampled keyboard
focus. Use the same checks for both conditions. Visual review is a rubric, not a pixel match to
library styles. Check light/dark page and surface separation, hierarchy, spacing, action
legibility, clipping, wrapping, and focus indication. Use objective defects as correction input;
do not ask one agent to imitate the other or reveal implementation advice. Keep evaluator bugs
separate from product defects. Freeze checker behavior before reading agent outputs; any later
checker correction must be documented and applied to both conditions.

Read source for identity correctness, required appearance APIs and forbidden private overrides.
An existing unsupported package behavior remains a finding even if the agent can work around it.
Native component selection is valid when it meets the requirements. If the installed package is
not used, report failure to observe adoption and do not attribute that app's maintenance costs to
library behavior. Do not add a mid-run instruction to force adoption. Count imported components
as observations, not a semantic score.

## Measurements

Report stage and cumulative input/output totals with cached input counted once; uncached input
plus output separately. Retain raw usage fields and missing telemetry. Report elapsed time,
commands, nonzero exits, correction requests and remaining defects. Measure normalized app/CSS
source, browser-check source and their sum. Retain stage snapshots, prompts, raw traces, package
hashes, screenshots, independent checks and review findings. Source size is not token usage.

The app starts from a blank scaffold and includes styling work. Maintenance tests an application
appearance change and a data/interaction change. It does not test library upgrades, months of
maintenance, broad app types, or all browsers. One sequence cannot establish reliable effect size.

## User clarification during execution

The first installed-package agent completed the initial task using only native controls. Whitney
clarified that adoption is outside this evaluation: assume a one-time project instruction to use
the library, then measure effectiveness over subsequent work. Retain the unprompted installed
attempt under `library-initial` as excluded evidence. Do not continue its maintenance sequence or
use its cost as evidence for library effectiveness.

Start one replacement library condition, `library-required`, from the identical original source
scaffold, with this sentence prepended: "Use the installed @trwhitney/component-library for
suitable UI components in this project. Keep native elements and custom application code where
appropriate." There is no documentation-path hint. Use the original maintenance prompt without
repeating that instruction. The native condition and all acceptance checks remain unchanged.
The comparison is native versus library-required. Report the excluded run's cost separately.
The replacement permits at most nine authoring attempts including the excluded one, retaining
the original per-condition stage/correction limits. This is an explicit user-directed scope
correction, not a rerun selected for a better score.

## Human review cost

Whitney notes that agent review underrepresents the style and feel issues they would find and
request changes for. Treat automated checks and coordinator visual review as requirement checks,
not human acceptance or equivalent design quality. Human review time, design judgment, revision
requests and the resulting agent tokens are unmeasured, not zero. Paired screenshots and runnable
apps were available at execution; those historical fixtures were later removed. Do not declare lifecycle superiority from agent-only totals or
assume the missing human cost favors either condition. Whitney subsequently clarified that subjective feedback should not be operationalized. No
human-directed revision round is planned. General-case usage reduction remains the goal, tested
through repeatable tasks and objective correctness/layout requirements.
