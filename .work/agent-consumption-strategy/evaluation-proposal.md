# Small comparative evaluation

## Accepted boundaries

Whitney authorized a small comparative evaluation. Optimize for a coding agent working in a
consuming application repository with this package installed. The no-library condition uses
React, native HTML, and CSS without another component library. An ongoing evaluation suite,
release gate, or prescribed consumer workflow is not part of this authorization.

Whitney requires reasonable discovery from the installed package without explicit outside
instruction. Do not provide an app instruction, task-prompt hint, or evaluator coaching that names
the agent entry point. Failure to discover relevant guidance is an evaluation finding.

## Completed comparison

Compare the same tasks in three conditions:

1. React and CSS without this library or another component library.
2. The installed current library and its current shipped guidance.
3. The installed library with the proposed agent-consumption improvements.

The first comparison tests the library's benefit against the chosen baseline. The second tests
the benefit of this strategy pass. Neither establishes superiority to other component libraries.

The pilot used three bounded task briefs, with one fresh run per condition, for nine runs. This
is diagnostic evidence, not a reliable estimate of success rates. Any additional repetitions need
a concrete unresolved question and a bounded run count.

The [task briefs](evaluation-tasks.md) covered:

- A preferences form with immediate and submitted settings, one exclusive choice, validation,
  and a submission result. This exposes field semantics and unnecessary state wiring.
- A searchable equipment register with an ordinary edit and consequential deletion. This exposes collection choice, overlay choice, and composition cost.
- A compact report with a trend, current status, and loading, empty, and error states. This
  exposes chart selection and feedback semantics beyond forms.

Write behavior-based briefs and checks before inspecting outputs. Do not name expected library
components in the task prompt. Allow multiple appropriate implementations, including native HTML
in every condition when it meets the need. The library conditions may additionally be assessed
for missed suitable library components; the baseline is assessed for equivalent semantic choices.

## Fairness and measurements

- Use equivalent prepared React application scaffolds. The library is already installed in its
  conditions, as requested. Keep initial setup cost separate from recurring implementation cost.
- Hold model, configuration, tools, stopping budget, task instructions, and correction rules
  constant. Use fresh contexts without this library repository or its implementation history.
- Give each condition its normal permitted documentation access. The improved condition must
  receive guidance through the package itself, not hidden extra coaching. Record how the agent
  discovers it, time/tool calls/tokens spent before reaching useful guidance, and whether it
  instead reads irrelevant package internals. Avoid repository-wide inherited instructions that
  would reveal the intended discovery path.
- Use the same observable behavior, accessibility, responsive-layout, and visual-coherence
  requirements. Do not require the baseline to reproduce private library implementation or its
  exact appearance. Native controls are valid solutions where appropriate.
- Record completion and failures first. Report incomplete work separately; missing functionality
  is not a token or code saving. Keep semantic component choice distinct from compilation.
- Capture actual reported input and output token usage, cached tokens separately when available,
  and tool calls and repair attempts. State whether reasoning tokens are included and how the
  runner reports context reuse. Missing telemetry remains unavailable rather than inferred from
  character counts.
- Measure final consumer-authored source and CSS using nonblank lines and characters. Exclude
  shared scaffolding, generated files, lockfiles, and dependency source. Include task-specific
  wrappers, helpers, styles, and data adapters. Keep revision effort separate from final size.
- Assess component appropriateness against a prewritten rubric of acceptable alternatives,
  including whether an existing library component's behavior was recreated unnecessarily.
- Preserve prompts, environment and package versions, raw usage reports, outputs, corrections,
  and rubric results. Report per-task outcomes and limitations rather than only one aggregate.

## Execution and results

All nine trials completed. The [pilot report](research/pilot-results.md) records the fixed runner,
model, eight-minute per-run limit, environment, independent checks, usage, and retained outputs.
The improved condition tested a documentation prototype with unchanged runtime JavaScript and
CSS. No mid-run coaching or reviewer repairs were supplied.

The prototype improved guidance discovery and reduced final consumer source overall. It did not
reduce total tokens or establish better semantic correctness across the tasks. Input, output, cached input, and reasoning output fields are retained. The reported total is
input plus output; it does not add the separate reasoning field again. Discovery observations
and repair attempts are retained in traces, not reduced to a causal latency metric.

Final size counts app and CSS content, including authored data literals. It excludes unchanged
bootstrap code, dependency files, evaluator scripts, and modified HTML titles. The pilot did not
perform a complete accessibility or visual audit. The report distinguishes checked behavior from
unverified requirements and documents task ambiguity and authoring-port interference.

Before any repeat, specify the reset-summary behavior and meaning of current day, reserve a
fixed browser port per trial, and agree on a bounded question. No further trials are scheduled.
